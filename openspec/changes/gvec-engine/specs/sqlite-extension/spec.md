## ADDED Requirements

### Requirement: Loadable extension entry point

The system SHALL ship a SQLite loadable extension exposing the standard entry point `sqlite3_gvec_init` generated by the `sqlite-loadable` crate (no hand-written C or raw FFI). Loading the extension MUST register the `gvec0` virtual table and the `gvec_query()` function.

#### Scenario: Load extension and register symbols

- **WHEN** the extension is loaded via `sqlite3_load_extension`
- **THEN** `CREATE VIRTUAL TABLE ... USING gvec0(...)` succeeds and `gvec_query(...)` is callable

#### Scenario: Idempotent init

- **WHEN** the extension entry point is invoked more than once in the same connection
- **THEN** no error occurs and registered objects remain functional

### Requirement: Extension version reporting

The system SHALL expose a `gvec_version()` scalar function returning a version string beginning with `v`.

#### Scenario: Version function

- **WHEN** `gvec_version()` is invoked
- **THEN** a string starting with `v` is returned

### Requirement: ABI and build artifact

The build SHALL produce a `cdylib` artifact loadable on the host platform (`libgvec.so` on Linux, `libgvec.dylib` on macOS) using only stable, documented SQLite C API calls.

#### Scenario: Build produces platform artifact

- **WHEN** the project is built on Linux
- **THEN** `libgvec.so` is produced and loads successfully in the SQLite CLI via `.load`

### Requirement: WAL and concurrency compatibility

The extension SHALL respect SQLite connection-level transactions and SHALL operate correctly when the database uses WAL journal mode with multiple readers.

#### Scenario: WAL reads

- **WHEN** the database is in WAL mode and a graph plus vector query is executed from a read connection while a writer is active
- **THEN** the read completes without corruption or error
